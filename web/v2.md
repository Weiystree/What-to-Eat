# Food Decision Agent V2 — 产品主线重构 + Persistent Fridge + Global Agent

## 0. 本次任务是什么

这是一次基于现有项目的 **V2 产品逻辑重构**。

不要把它理解成：

> “增加一个冰箱页面 / 增加几个新功能。”

本次真正要解决的问题是：

> 当前 App 已经拥有菜品识别、饮食记录、推荐、冰箱识别、聚餐、好友、附近餐厅、用户画像等能力，但这些能力目前更像多个平行功能，没有围绕用户最核心的饮食决策形成一条自然主线。

V2 要重新围绕用户真实使用 App 时的两个核心 Intent 组织产品：

### Intent A：我下一餐吃什么？

### Intent B：我正在 / 刚刚吃了什么？

所有页面、数据、AI 能力最终都服务于这两个 Intent。

同时增加一个全局 Food Agent：

> Agent 不属于某个 Tab，而是凌驾于整个 App 之上的智能交互层。

Agent 能读取 App 中已有的用户信息和状态，并调用已有功能完成任务。

# 2. 产品重新定义

产品一句话：

> **一个记得你吃过什么、知道你有什么、了解你和身边人的口味，并帮你决定下一餐吃什么的 Food Agent。**

核心不是：

> Food Tracking

也不是：

> Recipe App

也不是：

> Healthy Diet App

更不是：

> AI Chat App

核心是：

# Meal Decision

产品帮助用户减少：

> “下一顿到底吃什么？”

这件事的决策成本。

# 6. 「今日状态」从功能变成 Context

现有：

* hunger
* mood
* time
* scene
* crave
* personalNote

全部保留。

但是不要要求用户每天先完成一张“问卷”才能推荐。

它们应该成为 Recommendation Context。

例如用户点击：

> 帮我决定下一餐

Agent 可以轻量询问：

```text
现在什么感觉？

[ 很饿 ]
[ 一般 ]
[ 不太饿 ]

今天想：

[ 清淡点 ]
[ 吃爽一点 ]
[ 随便 ]

时间：

[ 15 min ]
[ 30 min ]
[ 不赶 ]
```

全部可跳过。

如果用户直接对 Agent 说：

> “今天很累，不想吃太油，而且最好二十分钟搞定。”

Agent 应自动解析：

```text
mood = tired
crave = light
time = 20min
```

而不是让用户重新点 UI。

# 8. Persistent Fridge

新增真正长期存在的：

# My Fridge

Fridge 是 Food Agent 的长期 Inventory Memory。

包含三个区域：

```text
冷藏 4°C

零度保鲜 0°C

冷冻 -18°C
```

每个 FoodItem 至少：

```javascript
{
  id,
  name,
  category,

  quantity,
  unit,

  storageZone,

  addedDate,

  expiryDate,
  expirySource,

  freshnessStatus,

  nutritionCategory,

  createdAt,
  updatedAt
}
```

storageZone：

```text
fridge
zero_zone
freezer
```

```text

↓

↓
```

```text

↓
```

> Fridge 是 State。

# 12. Freshness Engine

不要继续主要依赖 Vision 模型判断新鲜度。

图片可以辅助识别明显异常，但长期 Inventory 的 freshness 应主要由确定性规则产生。

建立：

```text
FoodShelfLife
```

根据：

```text
foodType
+
storageZone
+
addedDate
```

计算：

```text
expiryDate
freshnessStatus
```

状态：

```text
fresh
good
use_soon
urgent
expired
```

expired：

禁止进入 Recipe Recommendation。

如果用户输入包装上的明确到期日：

```text
expirySource = user_defined
```

优先使用用户日期。

# 14. 在家做的 Recommendation

Recommendation 优先考虑：

1. Allergy / Taboo Hard Filter
2. 临期食材
3. 已有食材覆盖率
4. 最近饮食
5. 用户口味
6. 当前状态
7. 烹饪时间

例如：

```text
今晚在家吃这个

🥦 西兰花鸡胸肉

20 min · 简单

为什么推荐：

鸡胸肉最好今天处理，
西兰花也放了几天。

而且你最近两餐蔬菜偏少，
这一餐刚好可以一起解决。

你已经有：
✓ 鸡胸肉
✓ 西兰花
✓ 鸡蛋

还缺：
○ 黑胡椒

[ 就吃这个 ]
[ 换一个 ]
```

# 26. Global Food Agent —— 本次最重要的 AI 升级

Agent 不属于 Today / Recommend Detail。

它应该成为：

# Global Agent

用户在 App 任意页面都可以唤起。

例如右下角一个轻量：

```text
✨
```

点击打开：

```text
Food Agent
```

用户可以随便问：

> 我今天晚上吃什么？

> 鸡胸肉还能吃吗？

> 我和 Amy 晚上附近吃什么？

> 我最近是不是吃太多面了？

> 帮我记一下我刚吃了海南鸡饭。

> 我昨天买了三个番茄，帮我放冰箱里。

> 我冰箱有什么快过期？

> 我想吃辣的，但今天不想太油。

Agent 不应该要求用户自己跳页面查数据再告诉它。

# 28. Agent 的技术原则

Global Agent 不应该：

> 每次把整个 localStorage 全部发给 LLM。

应该：

```text
User Message
↓
Intent Understanding
↓
决定需要哪些 Context
↓
调用对应 Tool
↓
获得结构化数据
↓
LLM Reasoning
↓
回答 / 执行动作
```

例如：

用户：

> 我和 Amy 晚上附近吃什么？

需要：

```text
getUserProfile
getFriendFoodProfile(Amy)
getRecentMeals
getTodayContext
getCurrentLocation
getNearbyRestaurants
```

不需要：

```text
完整 Community Feed
完整历史 Diary
完整冰箱
```

---

# 29. Agent 写操作必须 Confirmation

读取：

```text
冰箱有什么？
```

可以直接执行。

但是：

```text
帮我删掉鸡胸肉
```

或者：

```text
帮我记录这一餐
```

应该先展示结构化结果让用户确认。

例如：

```text
准备记录：

晚餐
海南鸡饭
无糖豆浆

[ 确认记录 ]
```

避免 Agent 猜错后污染用户长期 Memory。

# 30. Agent 和页面的关系

非常重要。

不要让 Agent 取代所有 UI。

正确关系：

```text
                Food Agent
              /     |      \
             ↓      ↓       ↓
          Fridge  Diary   Friends
             \      |       /
              \     |      /
               Decision
                  ↓
              下一餐吃什么
```

页面适合：

* 浏览
* 管理
* 确认
* 编辑
* 可视化

Agent 适合：

* 理解自然语言
* 综合 Context
* 做决策
* 调用能力
* 快速完成跨页面任务

# 32. 「饭搭子」而不是「一起吃」的原因

这一 Tab 不只是聚餐工具。

它承载：

```text
好友
+
Food Profile
+
邀请码
+
一起吃
+
朋友 Meal Sharing
```

所以建议使用：

# 饭搭子

页面顶部主要 CTA：

```text
和朋友一起吃？
[ 帮我们决定 ]
```

下面：

```text
我的饭搭子
```

再下面：

```text
朋友最近吃了什么
```

这样保留原 Community 的情感价值，同时让社交数据真正参与 Meal Decision。

```text
recommendGroupMeal
```

三种模式共享：

* Profile
* Diary
* Today Context
* Allergy Hard Filter

但额外 Context 不同。


## Eating Out

```text

```

## Group

增加：

```text

```

# 37. 本次最重要的判断标准

开发完成后，请不要只判断：

> 页面有没有实现。

而要用下面几个问题验收。

### Q1

用户打开 App 后，是否能在几秒内知道：

> “我要决定下一餐”或者“我要记录这一餐”？

### Q2

用户选择「在家做」时，是否无需重新拍冰箱？

### Q3

用户选择「出去吃」时，Agent 是否真正使用了 Location + History + Preference？

### Q4

用户选择「和朋友吃」时，是否真正使用朋友的 Food Profile？

### Q5

吃完以后，是否只需要记录一次，就同时成为 Diary / Agent Memory / Optional Share 的数据？

### Q6

用户不想点任何页面时，是否可以直接和 Global Agent 说自然语言完成相同任务？

### Q7

页面和 Agent 是否共享同一份真实 State，而不是各自维护重复数据？

如果这 7 个问题都成立，V2 才算真正完成。

# 38. 最终产品原则

不要把这个 App 做成：

> AI + 菜谱 + 冰箱 + 社区 + 日记 + 聚餐

六个功能的集合。

它应该是一个：

# Food Decision System

底层长期知道：

```text
我是谁
我喜欢什么
我不能吃什么
我最近吃了什么
我家里有什么
什么快过期
我现在什么状态
我和谁吃
他们喜欢什么
我现在在哪里
附近有什么
```

然后在用户最需要的时候回答一个极其简单的问题：

# 「所以，我下一餐到底吃什么？」

用户吃完之后：

# 「告诉我你最后吃了什么。」

这个结果重新成为下一次决策的 Context。

最终形成：

```text
Know Me
   ↓
Know My Food
   ↓
Know My Context
   ↓
Decide My Next Meal
   ↓
I Eat
   ↓
Remember It
   ↓
Know Me Better
   ↺
```

Global Agent 则是整个系统的自然语言入口。

**UI 是能力，Data 是 Memory，Agent 是 Intelligence，Meal Decision 是最终目标。**
